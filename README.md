# PipeGuard checker core

A small reference checker for finite, statically resolved, single-CTA SM90 PGIR programs. It is DSL-neutral and intentionally fail-closed.

## Install and run

```bash
python3.12 -m pip install -e '.[test]'
python3.12 -m pipeguard validate tests/fixtures/safe_handoff.json
python3.12 -m pipeguard normalize tests/fixtures/safe_handoff.json
python3.12 -m pipeguard check tests/fixtures/safe_handoff.json
python3.12 -m pipeguard check tests/fixtures/safe_handoff.json --engine exhaustive --pretty
python3.12 -m pipeguard check tests/fixtures/safe_handoff.json --engine crosscheck
python3.12 -m pipeguard explain tests/fixtures/safe_handoff.json
pytest
```

Every command writes deterministic compact JSON by default; pass `--pretty` for indented output. `check` and `explain` return one of `SAFE`, `SYNC_HAZARD`, `DATA_HAZARD`, `UNSUPPORTED`, `INCONCLUSIVE`, or `INTERNAL_ERROR`, and include top-level execution `statistics`.

## Reference semantics

Each actor advances in sequence order. Explicit `depends_on` references and protocol waits may additionally block a program event. Synthetic transitions are separate from program events: a `TmaLoadIssue` opens a global-source read window and a shared-destination write window, then enables one stable transaction-completion transition; only that transition credits bytes. A phase-completion transition is separately enabled when arrival count is zero and completed bytes equal expected bytes. It publishes the logical generation and advances the barrier; only then may events for the new current generation mutate barrier state. Future-generation arrivals or transaction operations are never buffered in a lookahead slot. Raw parity is valid only when it equals `logical_generation % 2`.

A `CP_ASYNC` resource keeps independent state per owner. `CpAsyncIssue` stages a global-read/shared-write operation; `CpAsyncCommitGroup` assigns the next gap-free group sequence and creates stable group and `GROUP_COMPLETE` identities. Nonempty group completions are synthetic and ordered per owner; an empty group is completed synchronously at commit, as required by its trivially-complete PTX semantics, and therefore has no completion anchor. `CpAsyncWaitGroup(N)` advances only after all but at most the `N` most recent committed groups have completed, records an observed frontier, and rejects staged-but-uncommitted operations. At most eight uncompleted groups are supported; the declared resource capacity may conservatively be smaller, and held-completion exploration detects capacity overflow schedules.

A `WGMMA` resource requires complete aligned 128-lane warpgroup owners. `WgmmaFenceOperand` records explicit shared-operand coverage before issue; issue and gap-free commit create separate ordered `OPERANDS_RELEASED` and `RESULT_READY` endpoint streams. `WgmmaWaitGroup(N)` explicitly names which endpoint it observes, so operand reuse cannot be justified by a result-only wait and accumulator access cannot be justified by operand release. Capacity counts a group until every endpoint completes. Empty WGMMA commits are fail-closed because the NVIDIA PTX contract checked for this checkpoint does not establish cp.async-style trivially-complete behavior.

A `TMA_STORE` resource stages explicit shared-source/global-destination transfers and commits them into ordered `SOURCE_RELEASED` and `GLOBAL_COMPLETE` endpoint streams. `GLOBAL_COMPLETE` has a typed prerequisite edge from the same group's source release. `TmaStoreWaitGroup(N, READ_ONLY)` observes only source release, while `GLOBAL` observes destination completion; therefore read-only wait permits shared-source reuse but cannot justify reading the global destination. Capacity retains a group until both endpoints finish, and empty store groups remain fail-closed.

A producer-consumer channel owns a fixed number of physical slots with explicit logical phases. `ChannelCreate` initializes producer-available slots; acquire/commit records producer ownership, commit enables an independent stable handoff, consumer wait observes that publication, and release advances the slot phase. A next-phase acquire blocks until the prior consumer release. Typed channel visibility follows producer commit→handoff→consumer wait and consumer release→next producer acquire; `control_only` channels order execution but never discharge a data conflict.

CTA and named barriers use a separate collective FSM. Every `BarrierArrive` covers the issuing actor's complete lane set; the resource capacity must exactly match its disjoint participants, and a CTA barrier must cover the whole CTA. A stable synthetic release is enabled only after all required lanes arrive. `BarrierObserve` blocks until that invocation releases. Release order and memory visibility are separate: a typed visibility mask grants only its declared shared/global/tensor domains, while `control_only` grants no data visibility.

The deterministic scheduler always chooses the lowest stable synthetic completion ID before the lowest `(actor_id, sequence_number, event_id)` program event. The default `maximal` engine implements that order with a hierarchical static-rank word bitmap and delta notifications rather than repeated full enabled-transition scans. Dependencies, blocked waits, future-generation phase followers, TMA spawns, changed barrier resources, collective releases, changed commit-group owner streams, and changed channel slots explicitly notify the ready index.

Held anchors are incremental streams: one stream per actor program sequence, one naturally ordered lifecycle/generation phase stream per resource, ordered typed group-completion streams per `(resource, owner, endpoint)`, one channel handoff stream per `(resource, slot)`, and singleton streams for TMA-load completions without explicit ordering semantics. Each stream starts from one fresh state. It holds its first anchor, runs to candidate-ready quiescence, records the full software-actor frontier, installs the next hold, and only then releases the old anchor. A typed `END` marker releases and flushes the final anchor. Invalid released candidates are applied and reported, while genuinely blocked quiescent states retain a stuck witness. The canonical maximal run uses the same incremental scheduler. Compact traces retain only stable step, transition, and kind fields; deterministic statistics certify stream counts, transition work, notifications, boundary evaluations, and zero full scans/clones/prefix replays.

Let `N_ext` be the number of program transitions, finite TMA/group completions and collective/phase releases, plus explicit dependency references; let `T_eff` be the number of non-empty program-actor, barrier phase/release, commit-group, channel-slot, and independent async-engine anchor streams. The implementation work bound is `O(T_eff * N_ext)` plus emitted boundary entries. It does not claim one shared mutable state across unrelated streams. `exhaustive` retains memoized all-state exploration as the independent small-model oracle. `crosscheck` compares complete boundaries for `SAFE` and `DATA_HAZARD`; for an early protocol result it compares only the verdict because the engines may select different deterministic witness prefixes.

The data checker constructs a full-boundary PDG with program-order, explicit dependency, arrival/release, issue/group/completion, and completion/wait edges. Shared visibility requires a matching actor/resource/generation arrival→phase→wait handoff; arbitrary waits do not make a path visible. It checks point read/write conflicts, TMA-load/cp.async source and destination windows, TMA-store shared-source and global-destination windows, WGMMA shared-operand windows through operand release, and WGMMA register-accumulator windows through result readiness. A group wait directly closes a window only for its owner; cross-actor publication is never inferred from `depends_on`. A `ProxyFence` may publish a generic write to an async read only for the supported CTA-scope `GENERIC → ASYNC_COPY/TMA/TENSOR_CORE` direction, when it is issued by the writer, lies between the write and issue in the PDG, fully covers the async source region, and carries the matching typed visibility mask. The reverse async-to-generic direction is never inferred from a symmetric fence; it requires observation of the corresponding typed completion. Unknown aliases, unresolved participant/parity facts, unknown fields/events, and unsupported protocol kinds never produce `SAFE`.

## Assurance scope

The held-anchor theorem applies to the fresh, transaction-free mbarrier core with its static actor and phase streams. Transaction completions, multi-lifecycle behavior, collective releases, cp.async groups, WGMMA/TMA-store typed endpoints, and channel handoff streams are supported by the implementation and covered by focused tests, but are stated conservatively as extensions crosschecked against the independent exhaustive oracle rather than as part of that theorem.

## Deliberate unsupported scope

PGIR v1 reserves typed resource/event fields and collision-safe synthetic identities for CTA/named barriers, commit groups, typed completion endpoints, channels, proxy visibility, and explicit async-engine ordering. Only the listed implemented FSMs and typed visibility transfers expand SAFE scope; remaining resource/protocol combinations stay fail-closed. Optional `engine_id`/`engine_seq` evidence on TMA-load or cp.async issue events is validated against a gap-free `ASYNC_ENGINE` stream, but cross-operation completion ordering is not yet used to prove safety. TMA completions therefore remain conservative singleton streams; cp.async uses only its intrinsic per-owner committed-group order.

Known PGIR events outside the implemented mbarrier/TMA-load/TMA-store/CTA/named-barrier/cp.async/WGMMA/channel/proxy-visibility core (including fork/join and atomics) are recognized and reported as `UNSUPPORTED`; they are not ignored. Unsupported proxy directions or scopes, cluster/multi-CTA operations, dynamic participants, unresolved parity, symbolic/unknown aliasing, and non-finite control flow are also fail-closed.
