# Triton mutation validation

This note records the Triton compiler-defect mutations added as Suite 4 rules M8--M13. They target the pinned Triton checkout `61c02bcdba0ccc1cdfc89ba608aa1a1221a59e1f` on H100 with CUDA ptxas 12.9.86.

Each mutation adds a canary whose correct value is exactly zero and adds that value to the original kernel output. Therefore the intended output of the Dense GEMM, Grouped GEMM, Fused Attention, LayerNorm, and Softmax kernels is unchanged. Each of the five kernels is tested with its original workload and three boundary workloads. Every process has a hard timeout of at most 60 seconds.

| M10 runtime-true masked consumer | PipeGuard-positive data hazard | 8/20 | 12/20 | `tl.debug_barrier()` between store and load: 20/20 pass |

No case timed out or deadlocked.

Per-kernel mismatches for the non-universal synchronization mutations:

- M8: Dense GEMM 4/4, Grouped GEMM 0/4, Fused Attention 0/4, LayerNorm 3/4, Softmax 4/4.
- M10: Grouped GEMM 4/4 and Softmax 4/4; the other kernels pass.
- M11: LayerNorm 3/4 and Softmax 4/4; the other kernels pass.

M11 remains provisional because the precise source-level guarantee for a relaxed atomic exchange followed by a non-atomic load must be stated before it is used as a strongest semantics-preserving positive. M8--M10 do not have this qualification.

## Compiler evidence

M8--M10 exercise the current Coalesce defect reported in [Triton issue #11581](https://github.com/triton-lang/triton/issues/11581). `Coalesce.cpp` chooses a layout independently for every memory operation, while `CoalesceUtils.cpp` can cap a store at a smaller per-thread width than the following load. In M8, the same pointer SSA value becomes a `sizePerThread=[1,4], warpsPerCTA=[2,2]` store and a `sizePerThread=[1,8], warpsPerCTA=[4,1]` load. The emitted PTX has `st.global` immediately followed by `ld.global`; the passing control adds `bar.sync 0` between them.

A minimal unique-address M8 capture is accepted by PipeGuard and reports `DATA_HAZARD / UNORDERED_CONFLICT`. Full operator captures currently stop after snapshot creation with `TRITON_EXECUTION_SCOPE_UNRESOLVED`, because the frontend requires execution-scope evidence for every operation when the original kernel's protocol events are mixed with the canary's global-memory events. This is a frontend coverage limitation, not a numeric or lowering failure.

M12 corresponds to the AxisInfo fix [Triton PR #11548](https://github.com/triton-lang/triton/pull/11548), which makes masked-load constancy account for the nonconstant `other` operand. M13 corresponds to [Triton issue #10924](https://github.com/triton-lang/triton/issues/10924), where `FuseNestedLoops` accepts a non-dominating assumption and incorrectly turns a zero-trip loop into an executing loop.

## Reproduction

The checked-in sources and patches are generated by `tools/mutation_suite_generate.py`. `tools/mutation_suite_triton_faults.py` contains the six deterministic canary transformations, recipe-signature augmentation, and runtime buffer initialization. The normal Suite 4 numeric runner understands these variants:

```bash
/usr/bin/python3 tools/mutation_suite_numeric_run.py \
  --output /tmp/pipeguard-suite4-triton-validation \
  --variant triton-softmax-source-m9-masked-store-roundtrip \
  --force
```

The driver uses `/usr/bin/python3` for corpus validation and launches Triton work in the configured `triton-pg` interpreter. Generated IR, CUDA, binaries, caches, and raw run output are intentionally not committed.
